# Задачи команды

Сначала прочитать `SPEC.md` и `contracts/api.md`. Контракты меняет только LEAD. Стартовый каркас передаётся команде вместе с этой версией; после начала работы каждый меняет только свою зону. Каждая задача ниже рассчитана на 15–30 минут и сдаётся рабочим коммитом своего участника.

## FRONTEND — `feat/frontend`, только `frontend/`

1. **Выбор мер, 25 мин.** Задача: улучшить редактор ровно пяти решений, показать направления, стоимость, лаг, городской/районный масштаб. Где: `frontend/src/`. Контракт: `GET /api/catalog`, `ScenarioRequest`. Готово, когда: можно собрать пример PDF и нельзя случайно добавить шестую меру; `npm run build` зелёный.
2. **Предварительная проверка, 20 мин.** Задача: подсветить дубли, более двух мер одного направления, нехватку бюджета и несовместимости; сервер остаётся окончательным валидатором. Где: `frontend/src/`. Контракт: `catalog.rules`, `catalog.conflicts`, ошибки 422. Готово, когда: каждая ошибка имеет понятное русское сообщение, чужие серверные числа не подменяются.
3. **Показатели до/после, 30 мин.** Задача: таблица/диаграмма пяти районов и десяти показателей, значения `<40`, районный прирост, общий Score. Где: `frontend/`. Контракт: `/api/baseline`, `SimulationResult.districts`, `critical_indicators`. Готово, когда: видно исчезновение критических S1/S2 Нуры в примере PDF.
4. **Объяснение и режим AI, 20 мин.** Задача: удобные блоки сильных сторон, рисков, советов; показывать `mode`/`notice`, загрузку, ошибки и повтор. Где: `frontend/`. Контракт: `/api/simulations/analyze`. Готово, когда: fallback никогда не представлен как живой ответ LLM.
5. **Сравнение двух наборов, 25 мин.** Задача: сохранить один результат локально и сравнить со следующим; исходные данные одинаковы. Где: `frontend/`. Контракт: существующий `/evaluate`, `dataset_version`. Готово, когда: перенос M7 в Есиль меняет Score и это видно без нового API.
6. **Готовность демо, 20 мин.** Задача: адаптивность, клавиатура, читабельность, кнопка восстановления примера PDF, проверка поведения при недоступном backend. Где: `frontend/`. Контракт: неизменный. Готово, когда: двухминутное демо SPEC проходит на экране ноутбука, сборка зелёная.

## OPS — `feat/ops`, `data/`, `tests/e2e/`, `deploy/`, `docs/`, `README.md`

1. **Сверка данных, 20 мин.** Задача: сверить 50 исходных значений, веса/население, 14 мер, лаги, эффекты, синергии и конфликты с PDF. Где: `data/`, отчёт в `docs/`. Контракт: `Catalog`. Готово, когда: нет расхождений; при исправлении данных отправлен CONTRACT_REQUEST на обновление fixtures и версии.
2. **Сквозные проверки, 30 мин.** Задача: сценарии старта, пример PDF, перерасход, дубли, несовместимость, повторный расчёт, fallback. Где: `tests/e2e/`. Контракт: `contracts/api.md`. Готово, когда: проверки запускаются одной конечной командой и обнаруживают нарушение бюджета или изменение базового Score.
3. **Сборка деплоя, 30 мин.** Задача: контейнеры/конфигурация выбранной платформы для backend и собранного frontend. Где: `deploy/`. Контракт: порт backend 8000, `/api/health`, VITE_API_URL при сборке, CORS_ORIGINS на сервере. Готово, когда: документирована воспроизводимая сборка без секретов в образе/репозитории.
4. **Публичная доступность, 25 мин.** Задача: опубликовать проект на согласованной платформе; настроить env, HTTPS, health-check. Где: `deploy/`, `docs/`. Контракт: все API v1. Готово, когда: URL доступен извне, frontend обращается к правильному API, нет ошибок CORS. Если нужны аккаунт/оплата/доступ — BLOCKER с конкретными требованиями.
5. **Воспроизводимость, 20 мин.** Задача: проверить README в чистом клоне и добавить фактические инструкции деплоя, URL и диагностику. Где: `README.md`, `docs/`. Контракт: существующие команды проверки. Готово, когда: третий человек может установить зависимости и повторить пример 56.54 без устных пояснений.
6. **Демо и эксплуатация, 20 мин.** Задача: прогнать 2-минутное демо, собрать чек-лист жюри и инструкцию восстановления, обеспечить доступность 24–28.09. Где: `docs/`, `deploy/`. Контракт: SPEC и API. Готово, когда: указаны ответственный, ссылка, режим AI и рабочий план восстановления.

## LEAD — следующие этапы

1. **Готово, включая живой smoke-test 23.09.2026.** OpenAI Responses API, Structured Outputs, общий deadline, один повтор, явный fallback и кэш реализованы. Реальный запрос подтвердил `mode=live`, `source=provider`, Score 56.54307. Настройка — `ai/README.md`, конечная проверка — `python -m scripts.check_ai`. OPENAI_MODEL по умолчанию gpt-4.1-mini; модель можно переопределить. Автоматические тесты никогда не используют личный ключ.
2. Уточнить требования к AI-рекомендациям: сравнивать только допустимые наборы. Если нужен function calling, передавать read-only инструменты через аргумент `tools`, ввести allowlist. Применение совета — только по действию пользователя.
3. При запросах команды синхронно обновлять `schemas.py`, JSON-примеры, `api.md`, тесты; оценивать необходимость для демо.
4. Перед интеграцией просматривать diff веток, запускать проверки; рабочие интеграции помечать `stable-N`. Сохранение/SQLite, роли, аудит — после обязательных функций, если нужны для сценария.

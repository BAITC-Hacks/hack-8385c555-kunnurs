# «Аким на 5 часов» — спецификация MVP

Источники: предоставленные 23.09.2026 PDF «HackAlem AI: Аким на 5 часов — AI-симулятор управления городом» (3 страницы) и «Датасет районов» (5 страниц). Численные правила ниже взяты из второго документа.

## Цель и границы

Пользователь выбирает пять городских мероприятий и получает воспроизводимый Astana Quality of Life Score, изменения районов и понятное объяснение компромиссов. Все пользователи начинают с одного датасета и бюджета 100. Данные синтетические; показатели не описывают реальную Астану и не являются прогнозом.

Архитектура: React/Vite → FastAPI → чистый расчёт → адаптер объяснения. Расчёт настоящий; реализован live-адаптер OpenAI Responses API со Structured Outputs. По умолчанию запрашивается live; без ключа или при ошибке возвращается явно обозначенный fallback. `AI_MODE=mock` принудительно включает шаблон. Для живой проверки нужен OPENAI_API_KEY в локальном `.env`; доступ модели и квоту подтверждает только реальный запрос. Публичный деплой и полный пользовательский интерфейс — следующие задачи. Хранение сценариев не требуется для основного сценария и пока не реализовано.

## Обязательные правила

- Ровно 5 мероприятий, каждое не более одного раза. Бюджет ≤100; остаток не даёт бонуса.
- Не более 2 мер на направление, значит минимум 3 направления. Все пять направлений представлены в каталоге.
- Районные меры требуют один из пяти районов; городские не принимают район (поле отсутствует или `null`).
- M1 и M3 несовместимы в любых районах; M4/M7 и M5/M13 несовместимы только в одном районе.
- Невалидный сценарий получает HTTP 422 с причинами и без Score.
- Порядок решений не влияет на результат. Каждый запрос начинается с неизменного исходного состояния.
- Клиент передаёт только ID мер и районов. Стоимости, эффекты, веса, бюджет и результат определяет сервер.

В общем ТЗ написано «5 решений по следующим направлениям», что допускает трактовку «по одному на каждое». Подробный датасет явно разрешает минимум 3 направления и приводит пример без транспорта. Принято более конкретное правило датасета; при разъяснении организаторов меняются SPEC и контракты вместе.

## Расчёт

Горизонт H=8 кварталов. Реализованная доля эффекта `(8 − L) / 8`.

1. Сложить исходные значения, все реализованные эффекты и фиксированные синергии.
2. Ограничить каждый показатель диапазоном [0,100] после сложения всех воздействий.
3. Балл района `D_d = Σ(w_k × I'_dk)`.
4. Средний городской балл `D_avg = Σ(pop_d × D_d)`.
5. `Score = 0.7 × D_avg + 0.3 × min(D_d) − N_crit`, где критично строго `<40`.

Веса T1/T2/E1/E2/S1/S2/B1/B2/C1/C2: 0.10/0.10/0.09/0.11/0.11/0.11/0.09/0.09/0.10/0.10. Население: Есиль 0.27, Алматы 0.24, Сарыарка 0.20, Байконур 0.13, Нура 0.16.

Синергии без масштабирования лагом: M1+M2 → T1+2 в районе M1; M10+M12 → B1+2 в районе M10; M5+M6 → E2+2 в районе M5.

Промежуточные числа не округляются. Ответ API округляет итоговые баллы/дельты до 6 знаков, UI отображает 2. Итоговый Score отдельно в [0,100] не ограничивается: PDF требует clip только показателей.

Проверенные ориентиры:

| Сценарий | Стоимость | Средний балл | Худший район | N_crit | Score |
|---|---:|---:|---:|---:|---:|
| Исходное состояние | 0 | 56.8624 | 49.18 | 2 | 52.55768 |
| M7 Нура, M8 Нура, M10 Нура, M12 город, M5 Сарыарка | 95 | 58.0776 | 52.9625 | 0 | 56.54307 |

`measure_effects` показывает реализованные приращения до clip и отдельные синергии. Это не независимые вклады в Score: минимум района, clip и критический штраф нелинейны. Для сравнения альтернатив нужно заново оценить полный допустимый набор.

## Критерии → функции → демо

| Критерий проверки | Функция | Момент демо |
|---|---|---|
| Одинаковые исходные условия | Версионированный каталог и `/api/baseline` | Показать бюджет 100, исходный Score 52.56 |
| Запрет перерасхода | Ограничение UI и независимая серверная валидация | Выбрать набор дороже 100; API возвращает 422 |
| Решения меняют показатели | Расчёт лагов, эффектов, синергий и районных дельт | Рассчитать пример PDF |
| Понятное объяснение AI | Адаптер получает проверенные числа, выдаёт сильные стороны/риски/советы | После live-интеграции показать ответ и источник чисел |
| Другой набор меняет Score | Повторный расчёт из одной базы | Перенести школу из Нуры в Есиль и сравнить |

Рубрика жюри: работоспособность 25, техническая реализация 25, README/воспроизводимость 25, применимость 15, развитие/оригинальность 10. Приоритет — закрыть первые три полностью. Наличие mock не закрывает обязательный AI-анализ в финальном продукте.

## Демо на 2 минуты

1. 0:00–0:20 — одинаковый старт, пять районов, слабые S1/S2 Нуры, базовый Score.
2. 0:20–0:45 — выбрать пять мер, показать стоимость и отказ при перерасходе.
3. 0:45–1:10 — пример PDF: 95 единиц, 56.54, +3.99, устранены два критических провала.
4. 1:10–1:35 — объяснение: приоритет слабого района, лаги, синергия камер и обращений. На mock явно говорить, что это заглушка; для защиты нужен live.
5. 1:35–2:00 — школа в Есиле вместо Нуры: повторный расчёт и другой Score; объяснить компромисс.

## Безопасность и дальнейшее развитие

Сейчас API не изменяет город, не принимает произвольные тексты, не вызывает инструменты и не требует персональных данных. Секреты только из `.env`, ошибки не отражают введённые значения, CORS ограничен конкретными адресами. CORS не является авторизацией.

Live использует фиксированный системный промпт, структурированный результат, только проверенные сервером данные и `store=false`. LLM выдаёт качественные списки сильных сторон, рисков и советов, без цифровых числовых утверждений; числовую сводку и Score формирует сервер. Выход с цифрами, пустыми списками, отказом или обрывом отклоняется. Это не доказывает фактическую корректность любого текста модели: рекомендации остаются гипотезами для проверки симулятором.

Общий deadline максимум 12 секунд (у frontend таймаут 15), на попытку также максимум 12 секунд; SDK делает не более одного повтора для временных ошибок в пределах общего deadline. Включён ограниченный кэш успешных разборов в памяти: 128 записей, TTL 1 час, отдельная отметка `source=cache`. При рестарте кэш очищается. Перед отправкой текстовые значения маскируются по email, телефону РФ/КЗ и 12-значному ИИН. Запросы и сырые ошибки в логи приложения не записываются, только фиксированный код причины fallback. API не предоставляет инструментов модели и не выполняет советы автоматически.

Сохранение/сравнение команд, SQLite/SQLAlchemy, audit log и подтверждение AI-предложений проектируются отдельно после MVP. Если появятся роли, заголовок X-Role годится только для демо; публичную авторизацию строить на проверяемой сервером идентичности.

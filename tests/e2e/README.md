# Сквозные проверки — зона OPS

HTTP-проверки используют pytest + httpx и модели `contracts/schemas.py`. Это проверки API; клики и отображение в браузере проверяются отдельно по `docs/judges-checklist.md`.

## Против сервера, который запустил человек

PowerShell, из корня проекта после установки зависимостей:

```powershell
$env:API_URL = 'http://127.0.0.1:8000'
python -m pytest tests/e2e -q -rs -p no:cacheprovider
```

`API_URL` — origin без `/api`, учётных данных, query и fragment. По умолчанию `http://127.0.0.1:8000`. Невозможность подключения или таймаут первоначальной проверки дают SKIP для HTTP-тестов; HTTP 500, неправильные ответы и ошибки после успешной проверки доступности дают FAIL. SKIP не доказывает работоспособность. `test_offline.py` выполняется локально независимо от доступности API.

## Без слушающего сервера

```powershell
python -m pytest tests/e2e --in-process --expected-ai-mode mock -q -p no:cacheprovider
python -m pytest tests/e2e/test_api.py --in-process --expected-ai-mode fallback -q -p no:cacheprovider
```

`--in-process` явно включает FastAPI TestClient. Он проверяет обработку HTTP внутри Python-процесса, не проверяя сеть, TLS или хостинг. Второй запуск проверяет текущий `AI_MODE=live`, который по контракту возвращает fallback. После реализации настоящего LLM эта проверка должна быть согласована с LEAD и моделировать отказ провайдера без реального платного вызова.

Полный конечный прогон: `powershell -File deploy/check.ps1 -Python .venv/Scripts/python.exe` либо `bash deploy/check.sh` с активированным окружением. Включает обязательный `scripts/check.py --require-frontend`, OPS mock и fallback проверки; ничего не устанавливает и не запускает серверы.

## Покрытие и ограничения

- Все пять эндпоинтов, схемы ответов и ошибок, исходный Score и пример PDF.
- Бюджет 100/перерасход, число мер, дубли, направления, районы, три несовместимости.
- Повтор и перестановка решений, другой сценарий, неизменность исходных данных.
- Prompt injection в дополнительных полях, вложенных описаниях, ID и подменённом каталоге; отказ до AI.
- Подмена Score/стоимости/весов, некорректный JSON, отсутствие введённых строк и внутренних деталей в ошибках.
- Захваченные Python-логи при `--in-process`; при удалённом запуске логи сервера и reverse proxy требуют отдельного просмотра.
- Раздача статики через deploy-модуль и отказ в доступе к `.env`, `.git` и исходникам.

Ролевой доступ не реализован и не заявлен в SPEC; тестов несуществующих employee/admin нет. Устойчивость настоящей LLM к заражённому внутреннему датасету этими тестами не доказана. Отчёт: `docs/security-report.md`.

## Конечная проверка в браузере

После запуска контейнера человеком: `node tests/e2e/browser_smoke.mjs http://127.0.0.1:8000`. Нужны Node.js 22+ и установленный Edge/Chromium. По умолчанию используется стандартный путь Edge в Windows; для другого браузера задайте `BROWSER_EXECUTABLE`. Дополнительные npm-пакеты не нужны.

Скрипт открывает отдельный headless-профиль, проверяет старт, нажимает расчёт, переносит школу в Есиль и пересчитывает. Проверяет 52.56 / 56.54 / 55.30 и origin API. Затем закрывает свой браузер и удаляет только свой временный профиль. Проверка не заменяет ручную оценку внешнего вида или публичной доступности.
